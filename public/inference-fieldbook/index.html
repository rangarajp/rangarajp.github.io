CHAPTER 01

Know Your GPU.

Before we ask a language model to think, we need to understand the machine doing the work. What can it store? How fast can it move numbers? How quickly can it multiply them?

No GPU knowledge required. We'll start with an analogy, experiment with visual models, and finish with real measurements from an NVIDIA RTX A3000 laptop GPU.

The guiding idea

A GPU's performance depends on two things: moving numbers and calculating with numbers. A program can be limited by either.

01 / The machine

A GPU is a factory for numbers.

Imagine a factory. A warehouse holds raw materials. Workers perform operations. A delivery system carries materials to the workers. If the delivery system is slow, workers wait. If workers are slow, materials pile up.

A GPU works similarly. VRAM stores large arrays of numbers. Streaming multiprocessors (SMs) run calculations in parallel. Smaller, faster memories help supply data to the SMs. Some calculations use specialized Tensor Cores designed for matrix operations.

Three different ideas: capacity, bandwidth, and compute

Capacity answers “How much fits?” Your GPU has 6 GiB of VRAM. Bandwidth answers “How many bytes can move per second?” Compute throughput answers “How many arithmetic operations can finish per second?” A large memory is not necessarily a fast memory.

02 / Moving data

Every calculation needs its ingredients.

Suppose we copy 16 million numbers from one GPU memory location to another. Each number is stored as FP16, which occupies 16 bits, or 2 bytes. The source holds 32 million bytes. Copying also writes 32 million bytes to the destination.

Our notebook measured a median of 0.269464 milliseconds across nine trials. A millisecond is one thousandth of a second.

Bandwidth = bytes moved ÷ seconds elapsed
64,000,000 ÷ 0.000269464 ≈ 237,500,000,000 bytes/s
≈ 237.5 GB/s

This is effective bandwidth for this copy experiment. It is not a claim that every GPU operation transfers data at this speed.

What this means for AI

A language model contains millions or billions of learned numbers called weights. Before the GPU can use a weight, the data must be accessible to the computing units. Moving weights can become a major part of inference time.

03 / Doing the math

Why GPUs multiply matrices.

A vector is a row or column of numbers. A matrix is a rectangular grid of numbers. Neural networks use matrix multiplication repeatedly to transform their inputs.

Take a tiny example. We have a 2×3 matrix and a 3×1 vector. To compute the first output, multiply corresponding entries and add them: 1×2 + 2×1 + 3×4 = 16. The second output is 4×2 + 5×1 + 6×4 = 37.

A FLOP is one floating-point arithmetic operation. FLOP/s is a rate, not a total. A trillion operations per second is one TFLOP/s. A matrix–vector multiplication is often called GEMV; matrix–matrix multiplication is GEMM.

Our experiment uses a 4096×4096 weight matrix. When it multiplies 512 input columns, the conventional approximate arithmetic count is:

FLOPs ≈ 2 × 4096 × 4096 × 512
≈ 17.18 billion operations

At the measured 0.3928 ms, that corresponds to 43.73 TFLOP/s achieved for this particular GEMM workload. It is not a universal GPU peak.

04 / Doing more with the same weights

Why doing more work together can be faster.

Imagine opening a large cookbook to prepare one dish. You spend time fetching the book for just one recipe. Now imagine preparing many dishes from the same book while it is already open. You do more useful work per book retrieval.

Similarly, a matrix multiplication may reuse the same weight values across many input columns. The opportunity for reuse grows with batch size (here, the number of input columns). The important concept is arithmetic intensity: useful calculations per byte transferred.

05 / Finding the limiting resource

Two different speed limits.

Return to the factory. Sometimes the workers can calculate faster than materials arrive. Other times, materials arrive quickly but the workers cannot process them any faster. These are the memory-bound and compute-bound situations.

The roofline model captures the two limits. A sloped line represents performance constrained by bandwidth. A flat line represents a compute throughput ceiling. Their intersection is called the ridge point.

Instrument E · Explore the rooflineConceptual model

The line uses measured proxies (237.5 GB/s copy and 43.73 TFLOP/s GEMM). It is an illustrative empirical roofline, not a validated device peak. Points use idealized traffic assumptions.

Attainable performance ≤ min(compute ceiling, bandwidth × arithmetic intensity)

Picture two teams in a factory

The delivery team brings materials; the production team turns them into finished goods. When deliveries are slow, workers are ready but have nothing to process. When production is slow, deliveries pile up and wait. That is the central idea behind the roofline.

Left of the ridge · Workers waiting

There is little computation for each byte delivered. More arithmetic power alone cannot fix slow data arrival. Reusing data and reducing transfers are the useful strategies.

Right of the ridge · Workers busy

Data is reused enough to keep arithmetic units occupied. Better matrix kernels, tiling, and Tensor Core utilization become important.

Why this matters for LLM inference

When an LLM generates a single token, it may need to read large weight matrices for relatively little computation. When it processes many prompt tokens together, it can reuse those same weights. This helps explain why token-by-token generation and prompt processing have different performance characteristics. The roofline helps us predict which optimization is worth trying first.

Our two proxy values intersect at approximately 184 FLOPs/byte. A workload below that intensity is more likely to face bandwidth pressure under this simplified model. A workload above it has enough reuse to potentially approach the compute ceiling. Actual results can be below either ceiling.

06 / Being a careful experimenter

GPU measurements can fool us.

The CPU often queues GPU work and continues before the GPU has finished. Timing only the CPU instruction that launches a kernel can therefore give a misleading answer. CUDA events can measure elapsed GPU time when used and synchronized correctly.

We also warm up the GPU, run repeated trials, report medians and variation, and record workload shapes and data types. Profiling tools can add overhead, so a profiled duration is not automatically comparable to an unprofiled CUDA-event duration.

Our rule for the whole book

Every performance number must say whether it was measured, calculated, or illustrative. We never use an illustration to claim that a performance optimization has been proven.
